# ADR-008: эксплуатация и защита данных

Статус: Accepted. Дата: 2026-09-11.

## Контекст

Production-oriented система должна восстанавливаться после сбоев, ограничивать доступ к контактам и объяснять, почему синхронизация отстаёт. Backup без испытанного восстановления не подтверждает готовность.

## Решение

Раздельные app/migration роли БД, TLS, secret manager, изолированные среды, авторизация по филиалу и объекту. Сотрудники используют Django sessions с CSRF, secure cookies; публичный create использует серверную гостевую сессию и rate limits, управление записью — отдельный случайный токен с ограниченным scope. Токен передаётся в защищённом заголовке, не URL/логе; hash используется для проверки, replay-copy — шифруется с отдельным ключом. Browser flow должен учитывать CSRF и запрещать кеширование секретных ответов.

Минимизировать контакты и доступ к ним; в audit/outbox хранить ID и изменения деловых полей без raw request/телефона. Контакт для согласованной доставки читается непосредственно перед отправкой. Структурированные логи/метрики не используют PII или booking ID в labels. Секреты/контакты маскируются и в error tracing.

Предварительный операционный retention: контакт обезличивается через 90 дней после terminal, полный receipt собственного API — через 30 дней, аудит/tombstone — 365 дней после terminal. Для просроченных CONFIRMED заводится задача оператору, а не бессрочное молчаливое хранение. Неразрешённый инцидент ставит документированный retention hold. Сроки — инженерные предложения, не юридическое заключение; владелец утверждает основание, сроки, размещение и процедуру запросов субъектов до публичного запуска. Окно внешних повторов может потребовать отдельного срока идентичности без контактов.

Deletion/anonymization не ломает историю занятости и дедупликацию в пределах их гарантированного срока. Backups имеют отдельный срок хранения и ограниченный доступ; после restore повторно применяется журнал обезличивания, чтобы не вернуть уже удалённые контакты. PR-22 фиксирует удаление replay body в `PrivacyRedaction`; owner всё ещё обязан утвердить срок и основание до запуска. Потерянный ключ шифрования не восстанавливается из репозитория: процедура key backup/rotation входит в операционную готовность.

PITR и независимые backup обязательны, RPO ≤5 мин/RTO ≤60 мин — начальные цели. Runbook после восстановления останавливает внешние writes, проверяет локальную целостность, receipts/outbox/mappings и период возможной потери данных. Затем сверяет внешние наблюдения и возобновляет канал контролируемо. Миграции — expand/contract, откат приложения проверяется с новой схемой.

## Альтернативы

Полный request в логах облегчает диагностику ценой утечки. Один superuser БД увеличивает область ошибки. Только ежедневный backup не соответствует RPO. Автоматическое продолжение доставки после PITR может переотправить устаревшее состояние и скрыть пропавшие подтверждения.

## Последствия

Нужны observability, проверки прав, housekeeping, тестовый restore и владельцы operational gate. Автоматизация измеряет готовность, но не заменяет принятие retention и бюджета владельцем. Нельзя заявлять нулевую потерю при отказе узла без выбранной стратегии репликации.

## Проверка

AUTH-01, SEC-01, OBS-01, OPS-01/02; PR-03/14/21–24. Команды: `rtk proxy uv run pytest tests/security tests/operations`, `rtk proxy make recovery-check`. Критерий: нет доступа вне scope/PII в логах, восстановление укладывается в цели и не возобновляет канал до сверки. Recovery-команда создаётся позже и работает только с отдельным disposable окружением.
