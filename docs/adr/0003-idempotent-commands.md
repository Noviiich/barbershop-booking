# ADR-003: идемпотентность и устаревшие команды

Статус: Accepted. Дата: 2026-09-11.

## Контекст

Клиент может не получить ответ после commit и повторить запрос. Две команды могут использовать одну исходную версию записи. У внешнего канала нельзя предполагать неописанный idempotency header.

## Решение

Durable CommandReceipt в PostgreSQL с UNIQUE по server-derived scope, operation и key, каноническим fingerprint и минимальным response. Результат и изменения одной команды фиксируются атомарно. Внешний inbox использует те же гарантии. Авторизация проверяется до replay. Мутации существующего Booking требуют expected_version либо доказанный эквивалент причинности во внешнем контракте.

Политика no-op, ошибок, savepoints, неопределённого commit и retention определена в [booking-flow](../architecture/booking-flow.md). После удаления полного ответа tombstone не допускает повторного выполнения старого намерения в пределах опубликованного retention. Гарантии не продлеваются на бесконечное время без сохранённой идентичности.

## Альтернативы

Кэш Redis не атомарен с booking и может исчезнуть. UNIQUE внешнего booking ID полезен, но до ответа create такого ID может не быть. Hash телефона/времени смешивает новое намерение и повтор. Exactly-once transport через HTTP не принимается как реалистичная гарантия.

## Последствия

Повторы сохраняют исходный результат, включая устойчивый отказ, даже если текущее состояние изменилось. Нужны политика хранения, защита replay-ответа, scope гостевой сессии и обработка expiry. Без YG-03/04 соответствующие внешние команды остаются выключенными; локальное ядро от этого не зависит.

## Проверка

IDEM-01, TX-01, MOVE-01, YAN-02; PR-08/09/12/18. Команда: `rtk proxy uv run pytest tests/integration/test_idempotency.py tests/concurrency/test_replays.py`. Критерий: один эффект для параллельных повторов, conflict при изменении payload, отказ stale mutation, отсутствие повторной команды после crash/expiry.
