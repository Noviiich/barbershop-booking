# ADR-007: Яндекс — внешний канал

Статус: Conditional. Дата: 2026-09-11. Условие активации: YG-01–YG-06 из [документа интеграции](../architecture/yandex-integration.md).

## Контекст

Заказчик требует интеграцию онлайн-записи при сохранении БД как source of truth. Публичная спецификация не заменяет согласование партнёрского доступа и проверку повторов.

## Решение

Выделить адаптер contract → внутренние команды и внутреннее состояние → внешние проекции. Использовать официальный партнёрский API после проверки доступа, snapshot контракта и contract tests. Каталог/слоты читаются из нашей БД, все изменения принимаются общей транзакционной службой.

Feature flags действуют по connection и capability. При неподтверждённой идентичности create или причинности update соответствующий write не включается. Реальный wire mapping статусов, auth и ошибок фиксируется отдельно; здесь не изобретаются значения контракта. Способы подключения описаны в [справке Яндекса](https://yandex.ru/support/business-priority/ru/manage/booking).

## Альтернативы

Яндекс как master противоречит исходному требованию. Polling с last-write-wins не защищает занятость. CRM-посредник возможна, только если сохраняет синхронное решение нашей БД; двойное владение календарём неприемлемо. Автоматический импорт неизвестных внешних записей способен создать конфликт.

## Последствия

Локальный MVP не зависит от партнёрского onboarding. Срок запуска канала нельзя обещать до согласования. Понадобятся mapping, inbox/outbox, quarantine, сверка, мониторинг и runbook остановки канала. Если внешний контракт не обеспечивает нужную семантику, нужен новый ADR и явное описание ограничений.

## Проверка

YAN-01/02/03, REC-01; PR-16–20/26. Команда: `rtk proxy uv run pytest tests/contracts tests/integration/test_yandex_commands.py tests/integration/test_reconciliation.py`. Критерий: контрактные fixtures проходят, повторы не создают второй эффект, stale update не меняет бронь; доступ подтверждается человеком и sandbox, не mock-тестом.
