# ADR-002: БД защищает от двойной записи

Статус: Accepted. Дата: 2026-09-11.

## Контекст

Чтение свободного времени и последующий INSERT допускают гонку. Уникальные времена начала не защищают пересекающиеся визиты разной длительности. Одновременно может измениться расписание.

## Решение

В PostgreSQL действует GiST exclusion constraint по глобальному мастеру и занимаемому `tstzrange` `[)`, включая буферы, для всех статусов кроме CANCELLED. Не партиционировать Booking так, чтобы ограничение перестало покрывать весь ресурс. CHECK/NOT NULL запрещают пустые и некорректные интервалы; range согласован с временем и снимками.

Короткие явные транзакции READ COMMITTED блокируют строку мастера перед проверкой расписания/допуска и изменением Booking. Изменения расписания/каталога используют тот же протокол. Стабильный порядок locks, savepoints и ограниченные повторы зафиксированы в [booking-flow](../architecture/booking-flow.md). Primary обслуживает авторитетные чтения.

Механизм range/exclusion описан в [PostgreSQL](https://www.postgresql.org/docs/17/rangetypes.html). READ COMMITTED обеспечивает новый snapshot для следующего statement, но не заменяет блокировки и ограничения: [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html).

## Альтернативы

Только application lock теряется между процессами; Redis-lock добавляет lease/partition риски; SELECT FOR UPDATE только по найденным записям не блокирует пустой диапазон. SERIALIZABLE возможен, но требует системных повторов и не заменяет ясного DB-инварианта. Предсозданные дискретные слоты усложняют произвольную длительность и буферы.

## Последствия

Гарантия пересечений работает между каналами и при конкурирующих INSERT. Один мастер сериализует изменения даже непересекающихся визитов — осознанный компромисс стартовой нагрузки. Корректность расписания зависит от дисциплины всех писателей; нельзя выдавать её за cross-table constraint. Установку btree_gist нужно проверить у провайдера БД.
