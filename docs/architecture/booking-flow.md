# Бронирование: команды, транзакции и гонки

См. [инварианты требований](../product/requirements.md), [lifecycle](domain-model.md), [ADR-002](../adr/0002-postgres-consistency.md) и [ADR-003](../adr/0003-idempotent-commands.md). Все алгоритмы здесь — спецификация будущего поведения, не production-код.

## Предложение слота и подтверждение

GET availability читает primary, вычисляет кандидатов из расписания и вычитает занятые интервалы визитов. Полученный слот не резервирует ресурс. Два пользователя могут увидеть один слот; подтвердить его сможет одна команда.

Для одного мастера пересечение любых двух занятых интервалов неотменённых записей запрещает GiST exclusion constraint с btree_gist: сравнение идентичности мастера на равенство и `tstzrange` на пересечение. Уникальность `(barber, start)` не защищает разные начала пересекающихся визитов. Полуоткрытые интервалы `[10:00, 11:00)` и `[11:00, 12:00)` допустимы. Основание механизма: [PostgreSQL ranges](https://www.postgresql.org/docs/17/rangetypes.html), [Django ExclusionConstraint](https://docs.djangoproject.com/en/5.2/ref/contrib/postgres/constraints/) и [ADR-009](../adr/0009-remove-service-buffers.md).

## Создание

```mermaid
sequenceDiagram
    participant C as Канал
    participant A as Command service
    participant D as PostgreSQL
    participant W as Worker
    C->>A: Команда + идентичность повтора
    A->>A: Аутентификация, scope, формат
    A->>D: BEGIN; claim receipt по UNIQUE
    A->>D: Lock мастера; повторное чтение правил
    A->>D: Проверки; вставка booking с exclusion
    A->>D: Audit + outbox + receipt результата
    A->>D: COMMIT
    A-->>C: Успех + booking ID + version
    W->>D: Claim доступной доставки
    W->>W: HTTP после окончания транзакции claim
    W->>D: Записать результат доставки
```

1. Проверить credentials, принадлежность объекта/филиала, формат команды и допустимость канала. Нормализовать время в UTC, телефон и другие входные данные по версионированным правилам. Начало/конец и цену не принимать на доверии: сервер вычисляет окончательный интервал из снимка услуги.
2. Начать явную короткую транзакцию READ COMMITTED. Получить право на идентичность команды через уникальный receipt; параллельный запрос того же ключа ожидает исхода первого в пределах бюджета.
3. Если результат уже зафиксирован, сверить fingerprint и вернуть сохранённый ответ после повторной проверки доступа. Если fingerprint отличается, вернуть конфликт, не выполняя команду.
4. Заблокировать существующую строку глобального мастера `FOR UPDATE`. После получения lock заново прочитать допуск, актуальную услугу, расписание, исключения и политику. Использовать свежее время БД, проверить горизонт, lead time, сетку и полный занятый интервал.
5. Вставить Booking внутри savepoint с DB constraint. Конфликт времени — детерминированная бизнес-ошибка. Откатить savepoint, сохранить receipt отказа без Booking/audit события изменения/outbox и завершить внешнюю транзакцию.
6. При успехе в той же транзакции записать audit, исходящие события для нужных подписчиков, mapping канала и результат команды. Нет подписчика — нет обязательства внешней доставки, но доменное событие может сохраняться для аудита процесса.
7. Commit, затем HTTP-ответ. Потеря соединения при commit даёт неопределённый результат для клиента: повторить тот же ключ и проверить receipt, а не создавать новый ключ. Ошибка БД без надёжно сохранённого receipt не считается устойчивым бизнес-отказом.

`IntegrityError` обрабатывается после выхода из повреждённого savepoint; нельзя продолжать запросы внутри сломанного atomic-блока. Только известное имя exclusion constraint переводится в конфликт слота, остальные нарушения — отдельная диагностика. Основание обработки транзакций: [Django transactions](https://docs.djangoproject.com/en/5.2/topics/db/transactions/).

## Протокол блокировок

Общий порядок для команд: собственный CommandReceipt → глобальные Barber по возрастанию ID → Booking по возрастанию ID → append-only audit/outbox. В MVP команда визита блокирует одного мастера и одну запись. Доставка outbox не берёт lock мастера или booking.

Все изменения смен, исключений, допусков, состояния мастера и изменяемых настроек услуги/филиала, которые влияют на запись, обязаны сначала брать те же locks мастеров. Массовое изменение охватывает весь набор затронутых мастеров в стабильном порядке. Изменение набора допусков и настроек каталога дополнительно сериализуется lock строки филиала, взятым **до** locks мастеров; команды записи не берут lock филиала, но перечитывают настройки после lock мастера. Набор затронутых мастеров определяют под lock филиала; новые допуски добавляются только тем же путём. Для нескольких филиалов сначала все Branch по ID, затем все Barber по ID. Смешивать этот порядок с обратным запрещено.

Это намеренно простая сериализация изменений на одного мастера. Блокировать только найденные пересекающиеся записи недостаточно: в пустом слоте ещё нет строки для блокировки. Exclusion constraint остаётся последним барьером между записями даже при ошибке приложения; контроль расписания требует соблюдения общего протокола всеми писателями. Прямой SQL с обходом команд запрещён операционными правами и процессом изменений, а не магически предотвращён ORM.

Мастер/филиал записи неизменяемы в MVP, поэтому их ID можно прочитать до lock, затем обязательно перечитать Booking под lock. Если будущая миграция разрешит смену ресурса, алгоритм должен получить locks старого/нового мастера и повторно проверить принадлежность до изменения — отдельный ADR.

Плановые бюджеты: ожидание lock ≤1 с, statement timeout ≤2 с, общий HTTP deadline ≤4 с для адаптера с контрактным лимитом 5 с. Значения подтверждаются нагрузкой. SQLSTATE `40P01`/`40001` допускают не более двух повторов целой транзакции с jitter вне транзакции и в остатке deadline. Исчерпанный deadline/lock timeout → retryable failure, не «слот занят». Exclusion violation `23P01` → бизнес-конфликт без автоматического подбора другого времени. Основание: [PostgreSQL locks](https://www.postgresql.org/docs/17/explicit-locking.html), [isolation](https://www.postgresql.org/docs/17/transaction-iso.html).

## Идемпотентность собственного API

Каждая мутация требует `Idempotency-Key`; для изменения существующей записи также `expected_version`. Scope включает бизнес, principal либо серверный идентификатор гостевой сессии, канал/connection, операцию и target ID при наличии. Это серверный scope, не произвольный tenant из тела запроса.

Fingerprint включает каноническую команду, target и expected_version; исключает tracing и транспортные подписи. Изменение алгоритма канонизации версионируется. В БД действует UNIQUE на scope/operation/key. Receipt не создаётся отдельно заранее без возможности восстановления: для синхронной команды `processing` существует только в её незавершённой транзакции. После crash до commit новая попытка может выполнить команду; после commit получает прежний результат.

Устойчивые бизнес-результаты, включая отказ в занятом слоте, сохраняются. Повтор того же неуспешного ключа после освобождения слота вернёт тот же отказ; для нового намерения клиент создаёт новый ключ. Ошибки auth/формата до выполнения и transient 5xx не кэшируются как итог команды. Для параллельного ключа, не уложившегося в ожидание, собственный API возвращает retryable `503` с `Retry-After`.

Ответ хранится минимально, без лишних контактов; для гостевого create выдаётся токен управления, сохранённый в replay-ответе зашифрованно, а для проверки доступа — только его hash. Исходный response replay не обязан отражать последующие изменения записи: текущее состояние читается GET. Секрет из replay выдаётся лишь тому же гостевому scope; украденный ключ не даёт доступ из другой сессии.

Проектный retention: полные receipts собственного API ≥30 суток; затем остаётся tombstone идентичности до конца срока хранения записи/аудита. Поздний повтор с tombstone возвращает `410 IDEMPOTENCY_RESULT_EXPIRED`, не выполняет команду. Гарантия повторов ограничена опубликованным сроком хранения tombstone; его удаление согласуется с политикой данных. Для Яндекса retention должен покрывать согласованное окно повторов и время жизни внешней записи; срок не переносится из собственного API автоматически.

## Отмена, перенос и исход визита

Отмена берёт receipt и lock мастера/записи, проверяет права, срок, текущий статус и версию по таблице lifecycle. В одном commit меняет статус, повышает версию, фиксирует причину/audit/outbox. Слот становится доступен в БД при commit. Ошибка доставки отмены Яндексу не возвращает CONFIRMED. Повторное CANCELLED — no-op. Если другой запрос уже занял освобождённое время, отмену нельзя «откатить» из-за внешнего сбоя.

Перенос проверяет новую доступность под тем же lock и атомарно обновляет интервал существующего Booking. Старый интервал не освобождается отдельной транзакцией. При conflict вся попытка изменения откатывается до исходной записи; записывается только receipt отказа. expected_version защищает от запоздавшего переноса и конкурирующей отмены. Обновление на то же время с актуальной версией — no-op.

COMPLETED/NO_SHOW разрешены сотруднику после end_at, повышают версию и сохраняют историческую занятость. Автоматическое завершение по часам не предусмотрено. Отмена после начала запрещена в MVP; операционное исправление данных требует отдельной процедуры, а не удаления строки.

## Обязательные конкурентные сценарии

| Гонка | Допустимый итог | Тест |
| --- | --- | --- |
| 20 create, разные ключи, один интервал | Ровно один успех, остальные slot conflict при достаточном тестовом deadline | CON-01 |
| 20 create, один ключ | Один booking/receipt/audit/event, одинаковый успешный ответ | IDEM-01 |
| Разные начала, пересекающиеся интервалы | Не более одной неотменённой записи | DB-01 |
| Cancel и create на старое время | Create либо видит конфликт до отмены, либо проходит после commit отмены | CON-02 |
| Два переноса одной версии | Один меняет запись; второй version conflict | MOVE-01 |
| Перенос и create на новое время | Победитель один; проигравший перенос сохраняет старый интервал | MOVE-01 |
| Удаление смены/добавление перерыва и create | Либо изменение расписания отклонено, либо create отклонён | SCH-01, CON-01 |
| Complete и Cancel | Только переход с допустимыми временем, версией и статусом; терминальное состояние не перезаписано | LIFE-02 |
| Прямые независимые INSERT с обходом service | Exclusion всё равно запрещает пересечение | DB-01 |

Собственный API: `201` при create, `200` при командах/no-op/replay, при replay create сохраняется исходный `201`; `400` формат, `401/403` права, `404` недоступный/неизвестный объект, `409` слот/версия/переход/key mismatch, `410` истёкший результат, `422` правило времени/каталога, `429` лимит, `503` transient. Адаптер переводит эти причины в фактический контракт Яндекса, не копирует собственные HTTP-коды вслепую.
