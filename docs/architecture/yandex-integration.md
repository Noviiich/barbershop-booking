# Интеграция с онлайн-записью Яндекса

Дата исследования: 2026-09-16. Статус: архитектура адаптера принята; публичный контракт
зафиксирован нормализованным snapshot с hash и тестами. Доступ к партнёрской среде и
окончательная семантика контракта не подтверждены. В репозитории нет работающего подключения,
credentials или выданного партнёру raw OpenAPI. Текущее состояние gate и capability matrix:
[контрактный артефакт](../contracts/yandex-contract-status.md).

PR-17 добавил отключённые read routes и отдельные mapping-таблицы. Глобальный флаг и оба
per-connection read-флага по умолчанию `false`; до закрытия YG-01 routes отвечают `404`.

## Что подтверждено официальными источниками

Прямая интеграция требует согласования. Документация описывает вариант для крупных сетей с собственной CRM и CRM-партнёров с более чем 300 подключёнными компаниями; поэтому право отдельного барбершопа на доступ нельзя предполагать. Возможен путь через действующего партнёра. При подключении согласуются идентификатор партнёра и JWT-секреты окружений. Локальные изменения записи должны передаваться Яндексу. Источники: [подключение API](https://yandex.ru/support/business-priority/ru/manage/booking-api-partners), [способы онлайн-записи](https://yandex.ru/support/business-priority/ru/manage/booking).

В публичном контракте Maps Booking Partners API 1.0 Яндекс вызывает HTTP API партнёра: чтение организаций/услуг/ресурсов/доступности и создание, получение, изменение, отмену записей. Указаны JWT HS256 и сверка claims с запросом. Для операций booking указан timeout 5 с; создание отвечает 200, бизнес-ошибки — 422. Предварительная бронь необязательна. Есть указание на исходящий PUT об изменениях. Источник: [официальная спецификация](https://yandex.ru/maps/booking/partners/api/).

Публичное описание не устанавливает достаточный для нашего проекта контракт идентичности повторного create и порядка команд. Наличие optional `prebookingId` не доказывает наличие универсального operation ID. Нельзя подставить придуманный заголовок и считать задачу идемпотентности решённой. Это вывод архитектурного анализа, а не утверждение, что у партнёрской программы вообще отсутствуют дополнительные механизмы.

## Направления и граница доверия

Следующие правила — решения нашей системы.

| Поток | Поведение нашей системы |
| --- | --- |
| Яндекс → чтение каталога/слотов | Адаптер отдаёт проекцию primary БД с фильтром по connection/branch; слот не гарантирует резерв |
| Яндекс → создать/перенести/отменить | Проверка credentials и object scope → нормализованная команда → общий booking service → commit → контрактный ответ |
| Локальная команда → Яндекс | Outbox в локальном commit; worker отправляет требуемую контрактом проекцию |
| Яндекс → уведомление, если согласовано | Durable inbox + dedup; перевод только в разрешённую команду с доказанной причинностью |
| Сверка | Сравнение локальной версии и внешнего представления в пределах реально доступных read-возможностей |

Яндекс не назначает окончательное время и не определяет наличие записи в БД. При конфликте локальная команда отклоняется по контракту. Исторический внешний snapshot не является командой перезаписать booking. Если посредник подтверждает слот без синхронного решения нашей БД, такой вариант не сохраняет INV-01 для обещаний клиенту и требует изменения схемы интеграции до запуска.

Адаптер публикует capability matrix: `catalog_read`, `availability_read`, `create`, `reschedule`, `cancel`, `status_push`, `readback`, `prebooking`. По умолчанию writes выключены. Возможности нельзя включать по наличию токена без закрытых gate. Требуемые Яндексом взаимозависимые возможности включаются пакетом; частичное включение возможно только если принято партнёром.

## Идентичность, повтор и сообщения не по порядку

Локальные UUID не заменяются внешними ID. Contract booking ID может быть ID, который выдаёт наш backend; это уточняется в mapping, а не предполагается наличие двух разных ID. Уникальность ExternalMapping ограничена connection, окружением и типом сущности. Проверяются филиал, канал и принадлежность записи при GET/PUT/DELETE, даже если подпись корректна.

Синхронные внешние команды используют CommandReceipt/InboxReceipt в той же транзакции, что Booking и mapping. Идентичность: connection + operation + подтверждённый operation ID. Повтор с тем же ID и другим содержимым — контрактный конфликт/инцидент. Если wire-контракт не передаёт expected_version, адаптер должен опираться на согласованную причинность; нельзя подставлять «текущую версию» и этим разрешать устаревший перенос.

Hash телефона, услуги и времени нельзя считать надёжной идентичностью команды: он не отличает повтор от новой записи после отмены. Отсутствие стабильной идентичности не позволяет обещать exactly-once effects для внешнего create. До YG-03 сохраняется запрет write; при ином согласованном решении создаётся ADR с точным окном и потерянными гарантиями.

Если дополнительно согласованы асинхронные входящие события, inbox сохраняет событие до acknowledgement, затем processor выполняет общую команду; повтор узнаётся по event ID. Старые версии игнорируются с аудитом, разрыв последовательности запускает сверку. При отсутствии версии/ID сообщение карантинируется для выяснения, а terminal никогда не открывается внешним snapshot. Этот асинхронный путь не подменяет обязательный синхронный create.

## Сопоставление статусов

Доменные статусы описаны в [domain-model](domain-model.md). Точная таблица wire enum должна появиться в артефакте YG-02; пример из документации не считается полной семантикой enum.

| Локальное значение | Требование к адаптеру |
| --- | --- |
| CONFIRMED | Передать успешную принятую запись; wire-значение подтвердить контрактным тестом |
| CANCELLED | Передать отмену; входящий DELETE транслировать в CancelBooking с сохранением истории |
| COMPLETED / NO_SHOW | Передать исход способом, разрешённым контрактом; не придумывать одноимённые enum |
| Любая ошибка доставки | Обновить DeliveryState; локальный статус не менять |
| Неизвестное внешнее значение | Сохранить диагностическую причину, запретить произвольный переход |

Если контракт различает техническое подтверждение и итог визита, это разные проекции одного локального состояния. Политика no-op и echo фиксируется контрактом: событие аудита всегда сохраняется; ответ на входящую команду обычно уже сообщает её результат, поэтому обратная отправка того же изменения делается только при необходимости. Причинный operation ID не даёт бесконечной петле порождать новые доменные версии.

## Outbox и доставка

OutboxEvent неизменяем и фиксирует booking ID, версию и тип. Для каждой требуемой доставки существует отдельное состояние. Worker короткой транзакцией claim выбирает готовые записи через `FOR UPDATE SKIP LOCKED`, задаёт lease/owner token и завершает транзакцию до HTTP. Истёкший lease доступен для восстановления. Успех/ошибка фиксируются только текущим owner token, чтобы запоздавший worker не перезаписал локальный cursor.

Для пары connection + booking сериализуется отправка. Событие старой версии служит сигналом проверить актуальную проекцию: для snapshot-синхронизации можно объединить ожидающие версии и отправить последнюю, сохранив историю событий. События, которые контракт требует доставить по отдельности, не объединяются. Cancel нельзя потерять при coalescing; версия snapshot и подтверждённая версия записываются явно.

At-least-once: crash после внешнего успеха до локального ACK ведёт к повтору. Стабильный delivery ID передаётся как ключ только если это разрешено контрактом. При timeout результат считается неизвестным. Повтор безопасен лишь при подтверждённой идемпотентности операции или после readback. Если это не доказано, доставка переходит в состояние неопределённости и требует сверки/разбора.

Локальный lease не блокирует уже ушедший HTTP на стороне Яндекса. Без внешней проверки версии даже один worker не гарантирует отсутствие кратковременного регресса после сетевого timeout. При доступном version fencing посылать локальную версию; иначе после неопределённого результата выполнять readback/повтор актуальной проекции и периодическую сверку. Гарантия в этом режиме — eventual convergence при восстановлении связи и принятой идемпотентности PUT, а не строгий внешний порядок.

Retry-политика проекта: экспоненциальная задержка с full jitter, база 1 с, cap 5 мин, учёт `Retry-After`; после 20 неуспехов или 24 часов — parked с alert и возможностью ручного replay того же delivery ID. `429`, согласованные временные 5xx и сетевые сбои повторяются; ошибки схемы/неизвестного mapping — parked; auth errors приостанавливают connection и сигнализируют о credentials. Нельзя бесконечно повторять все 4xx. Конкретные статусы уточняются YG-02/05.

## Сверка и деградация

Каждые 5 минут worker проверяет backlog, застрявшие lease и локальные desired/acknowledged versions. Если есть внешнее чтение, сравнивает изменённые записи с перекрытием watermark; раз в сутки — все известные активные записи и недавно закрытые в пределах rate limit. Страница считается пройденной только после durable checkpoint; crash не теряет остаток. Нет readback — проверка ACK и повтор проекции являются только контролем доставки, а отсутствие полного внешнего списка не позволяет автоматически найти все внешние orphan. Эти ограничения явно выводятся в отчёт.

| Расхождение | Действие |
| --- | --- |
| Внешнее состояние старее локального | Переотправить актуальную проекцию, не менять Booking |
| Неизвестный внешний ID / запись без mapping | ReconciliationIssue и ручной разбор; не создавать конфликтующую локальную запись |
| Локальная запись не найдена удалённо | Проверить mapping и возможности восстановления; не создавать внешнюю сущность вслепую |
| Внешняя «отмена» обнаружена снимком | Выяснить источник/пропущенную команду; не выполнять last-write-wins |
| Дубликат или нарушение контракта | Изолировать capability, сохранить аудит, уведомить оператора через мониторинг |

При outage Яндекса локальные операции продолжаются, outbox накапливается, экспоненциальные retries ограничены. При outage нашей БД адаптер не подтверждает запись; интерфейс Яндекса может показывать устаревшие слоты, но backend отклоняет неподтверждённую команду. Circuit breaker ограничивает исходящие вызовы. Для отключения канала нужен согласованный способ снятия публикации; одного локального feature flag недостаточно для удаления внешнего виджета.

После PITR приостановить внешние writes/delivery, восстановить mappings/receipts, сверить период возможной потери commit и внешние наблюдения; пропавшие после восстановления подтверждения разобрать как инцидент, не импортировать автоматически. Затем контролируемо возобновить доставку. Проверки YAN-01/02/03, OUT-01/02, REC-01 и OPS-02 описаны в [testing-strategy](../testing-strategy.md).
