## Обязательные архитектурные правила будущей реализации

1. PostgreSQL — единственный источник истины для записи, занятости, расписания и каталога. Яндекс передаёт команды и получает проекции. Внешний ответ не переписывает доменные данные автоматически.
2. Все изменения бронирований проходят через один application service: HTTP, администратор, интеграция, фоновые команды. Запрещены обходные записи через Django Admin, signals, `bulk_update` или фоновые импорты.
3. Пересечение интервалов одного мастера запрещено exclusion constraint PostgreSQL. Проверка свободного слота сама по себе недостаточна. Не заменять гарантию БД mutex в процессе, Redis-lock или уникальностью времени начала.
4. Изменение записи, аудит, результат идемпотентной команды и outbox фиксируются атомарно. HTTP-вызов внешнего сервиса выполняется после commit отдельным worker.
5. Соблюдать единый порядок блокировок и правила повторов из booking-flow. Автоматический повтор не создаёт новую команду с новым ключом.
6. Отмена — переход состояния с сохранением истории. Успешная локальная отмена не ждёт Яндекс. Статус синхронизации не является статусом бронирования.
7. Временные моменты timezone-aware; хранение — UTC, календарь филиала — IANA timezone. Не полагаться на timezone ОС, фиксированное `+03:00` или naive datetime.
8. Контракт Яндекса проверять по официальной спецификации. Не изобретать endpoints, подписи, idempotency headers, статусы и гарантии порядка доставки. Не подтверждённая возможность явно помечается и закрывается до запуска канала.
9. Ограничения конкурентности тестировать на настоящем PostgreSQL с независимыми соединениями и commit. SQLite и mock ORM не подтверждают такие гарантии.
10. Секреты и контакты клиентов не помещать в git, fixtures, логи, trace, URL и payload outbox без обоснованной необходимости. Проверять доступ к объекту и филиалу при каждом запросе, включая идемпотентный повтор.

## Правила PR

Один PR соответствует одному шагу roadmap. Его описание содержит цель, изменения, acceptance criteria, автоматический тест, команды и фактический результат проверки. Будущие команды не выдавать за выполненные. Изменение инварианта требует нового ADR и обновления зависимых документов в том же PR. Не переписывать историю принятых ADR без отметки о замене.

Новые endpoints по умолчанию выключены или доступны только сотрудникам до готовности авторизации и проверок. Миграции совместимы с предыдущей версией приложения; разрушительные изменения выносятся в отдельный поздний PR. Пользовательские изменения и служебные каталоги сохранять; незапрошенные внешние сообщения и публикации не выполнять.
